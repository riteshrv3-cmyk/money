# Chapter 2.2 [SPINE]: मुख्य सुगावा: Memory ची उतरंड आणि Latency-पट्टी

चंदूचा प्रश्न: memory मध्ये खरंच हजारो पट फरक? उत्तर: हो,
आणि हा chapter पूर्ण Part 2 चा सर्वात महत्त्वाचा आहे. ही
latency-पट्टी प्रत्येक top engineer च्या डोक्यात कोरलेली असते.
भिंतीवर लावा.

**उतरंड: जवळ-छोटं-जलद-महाग ते दूर-मोठं-हळू-स्वस्त.** यंत्रातली
memory एका **उतरंडीत** असते: CPU जवळ थोडी-पण-वीज-वेगवान,
दूर भरपूर-पण-हळू. स्वयंपाकघराची उपमा: हातातलं (चाकू, सर्वात
जवळ, झटकन); ओट्यावरचं (मसाले, जवळ); फ्रिज (भाजी, थोडं
दूर); बाजार (सगळं, पण जायला वेळ). प्रत्येक थर मोठा पण दूर,
म्हणून हळू.

**Latency-पट्टी (2020 च्या दशकातले ढोबळ आकडे: तपासलेले):**

```
जागा              वेळ (ढोबळ)      उपमा (1ns = 1 सेकंद धरला तर)
CPU रजिस्टर       ~शून्य           आत्ता, हातात
L1 cache          ~1 ns           1 सेकंद (हातातलं)
L2/L3 cache       ~4-40 ns        काही सेकंद (ओट्यावर)
RAM (main memory) ~100 ns         ~2 मिनिटं (फ्रिज)
SSD (disk) वाचन   ~16-100 us      ~दिवस-दोन दिवस (बाजार)
HDD (जुनी disk)   ~2-10 ms        ~महिने (दुसऱ्या गावी)
एकाच DC मध्ये जाळं ~0.5 ms         ~आठवडे
भारत->अमेरिका जाळं ~180-250 ms     ~वर्षं! (दुसऱ्या खंडात)
```

**हे नीट बघा: RAM आणि SSD मध्ये ~1000 पट फरक; RAM आणि
जुनी disk मध्ये ~लाख पट; आणि दुसऱ्या खंडाशी बोलणं म्हणजे
(CPU च्या दृष्टीने) वर्षं!** म्हणून पट्टीच्या उजव्या टोकाला एक
स्पर्श म्हणजे CPU-दृष्टीने अनंत काळ. Book 5 चा latency (1.9:
अंतर = वेळ) आणि Book 4 चा memory-bound (6.1): दोन्ही या
एका पट्टीत.

**चंदूच्या केसचा मोठा तुकडा: "जवळ ठेवा."** आता चंदूला कळलं
की CPU आकड्यांची वाट का बघतो: जर आकडा RAM मध्ये (2
मिनिटं) किंवा disk वर (दिवस) असेल, तर CPU (जो सेकंदाला
अब्जावधी करतो) रिकामा बसतो. उपाय: **वारंवार लागणारं जवळ
(cache मध्ये) ठेवा.** आणि इथे जादू: CPU आपोआप हेच करतो:
वापरलेला आकडा L1/L2 cache मध्ये ठेवतो, म्हणून **पुढच्या
वेळी जवळून** (1 सेकंद, बाजाराला जाण्याऐवजी). Book 5 चं cache
(1.4), Book 4 चं prompt-cache: सगळं याच एका तत्त्वाचं:
**जवळ ठेवा, दूर टाळा.**

**आणि सर्वात मोठा व्यावहारिक धडा (code साठी):** जर तुमचं
code memory मध्ये **शेजारी-शेजारी** आकडे वापरत असेल (array:
1.2), तर CPU एका फेरीत जवळचे सगळे cache मध्ये आणतो
(जलद). पण जर आकडे **विखुरलेले** असतील (linked list, इकडे-
तिकडे pointers), तर प्रत्येक आकड्याला वेगळी लांब फेरी (हळू).
म्हणून अनेकदा array हे linked list पेक्षा **प्रत्यक्षात** खूप
जलद, Big-O सारखा असूनही: कारण cache. **हेच "same Big-O,
वेगळा वेग" चं रहस्य:** algorithm (Part 1) कागदावर सारखा,
पण हार्डवेअर (जवळ की दूर) वेग ठरवतं.

## इथे लोक काय चुकीचं समजतात

"Memory म्हणजे memory, वेग सारखाच." ~लाख पट फरक! आणि
हे न समजणं म्हणजे "cache का महत्त्वाची", "disk-वाचन का
टाळावं", "array का जलद" हे सगळं न कळणं. दुसरा गैरसमज:
"disk म्हणजे hard disk, हळूच." आधुनिक SSD जुन्या HDD पेक्षा
~100 पट जलद (पण RAM पेक्षा अजून ~1000 पट हळू). पट्टीवरची
नेमकी जागा माहीत असणं = कुठली कृती किती महाग हे आधीच
ओळखणं. ही पट्टी न जाणणारा engineer अंधारात optimize
करतो.

## नकाशावर

```
2.1  CPU: वेगवान पण आकड्यांची वाट बघतो
2.2  latency-पट्टी: L1(1ns) -> RAM(100ns, ~1000x) -> SSD
     (~दिवस) -> जुनी disk(~महिने) -> दुसरा खंड(~वर्षं); जवळ
     ठेवा (cache); array जलद कारण शेजारी (same Big-O, वेगळा वेग)
```

**सूत्रावर:** ही पट्टी सूत्राचं हृदय: जवळची जागा (cache) महाग-
पण-जलद, दूरची (disk) स्वस्त-पण-हळू. वेग हवा तर जवळ ठेवा
(महाग जागा); स्वस्त हवं तर दूर (हळू). प्रत्येक cache हा हाच
सौदा.

## स्वतः बघा (5 मिनिटं)

तुमच्या स्वयंपाकघरात/कामाच्या टेबलावर बघा: रोज लागणारं हाताशी,
कधीतरीचं कपाटात, क्वचितचं माळ्यावर. का? कारण हाताशी सगळं
ठेवता येत नाही (जागा कमी), आणि माळ्यावरचं आणायला वेळ.
हीच memory-उतरंड, तुमच्या घरात. यंत्रही अगदी हेच करतं:
वारंवारचं जवळ, क्वचितचं दूर.

चालू असताना, माझ्या फोनवर WhatsApp, गाणी, आणखी दहा
apps पण चालू असतात. एकच CPU, एकच memory: मग हे सगळे
एकाच वेळी कसे चालतात? कोण ठरवतं कुणाला कधी CPU मिळेल?
आणि माझं app दुसऱ्या app मुळे हळू होऊ शकतं का?"

> कशी चालतात, आणि कोण ठरवतं: पुढचे chapters. आधी "एक
> काम म्हणजे काय" (process/thread), मग "वाटप कोण करतं"
> (scheduling).
