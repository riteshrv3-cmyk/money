# Chapter 3.4 [SPINE]: चंदूच्या केसचा निकाल

गुप्तहेराचा शेवटचा deng. सगळे संशयित एका खोलीत, आणि चंदूच्या
"app कधीकधी हळू" चा पूर्ण निकाल. प्रत्येक chapter मधला तुकडा
आता एका पद्धतशीर तपासात जोडू: आणि हीच खरी debugging-कला
(Book 4, 5.2 चा error analysis, इथे हार्डवेअर-भर).

**पद्धत: मोजा, अंदाज नको (सर्वात मोठा धडा).** चंदूने आधी काय
**चूक** केलं ते बघा: तो अंदाजाने "मोठा server घेऊ" म्हणत होता
(Part 2, 2.1 ची चूक). पण जाणकार गुप्तहेर **अंदाज लावत नाही,
मोजतो** (Book 5, 1.12 चं observability). चंदूने प्रत्येक संशयिताला
मोजून तपासलं:

```
संशयित 1 (algorithm, Part 1): शोध O(n) होता का?
   मोजलं: नाही, hash केल्यावर O(1). [निर्दोष, आता]
संशयित 2 (आकडे दूर, 2.2): data disk वरून येतंय का?
   मोजलं: बहुतेक RAM/cache मध्ये. [बहुधा निर्दोष]
संशयित 3 (OS/गर्दी, 2.3-2.4): दुसरं app CPU खातंय का?
   मोजलं: सामान्य वेळी नाही.
संशयित 4 (RAM संपणं, 2.4): swap/thrashing होतंय का?
   मोजलं: गर्दीच्या वेळी RAM भरते, swap सुरू! संशयित सापडतोय.
संशयित 5 (concurrency, 3.1): lock वर threads थांबतायत का?
   मोजलं: होय: एका सामायिक गोष्टीवर सगळे threads एकाच
   कुलपाची वाट बघत रांगेत! मुख्य गुन्हेगार सापडला.
```

**निकाल: दोन गुन्हेगार, एकत्र काम करणारे.** चंदूचं app "कधीकधी"
(गर्दीच्या वेळी) हळू होतं कारण: (अ) गर्दीत RAM भरून swap सुरू
(disk-वेग, 2.4), आणि (ब) एका खराब-ठेवलेल्या lock वर सगळे
threads रांगेत थांबत (3.1: वेग-मारक कुलूप). दोन्ही फक्त गर्दीत
एकत्र येऊन app रांगवत होते: म्हणून "कधीकधी" (सामान्य वेळी
दिसत नव्हतं: Part 1 चा "लहान-प्रमाणात लपतं" धडा). **उपाय:**
lock चा वापर कमी करणं (कमी सामायिक गोष्ट, 3.1) + RAM
वाढवणं किंवा memory-वापर घटवणं. केस सुटली.

**खरी शिकवण (पूर्ण पुस्तकाची): debugging = पद्धतशीर तपास,
अंदाज नाही.** चंदूने काय शिकलं ते तुमचं सर्वात मोठं हत्यार:
(1) **मोजा** (observability), अंदाजाने "मोठा server" घेऊ नका;
(2) **एकेक संशयित** वेगळा तपासा (algorithm? memory? OS?
concurrency?): पद्धतशीर, घाईने नाही; (3) **अनेक कारणं एकत्र**
असू शकतात (इथे दोन); (4) **लहान-प्रमाणात लपतं** (गर्दीत
फुटतं). ही नजर: "हे हळू का" ला अंदाजाऐवजी तपासाने भिडणं:
हीच top engineer आणि नवखा यांतली सर्वात मोठी फरक-रेषा.
आणि AI-युगात (Book 4): agent code लिहील, पण **"हे हळू
का, कुठला संशयित"** हे पद्धतशीर तपासणारी नजर तुमचीच.

## इथे लोक काय चुकीचं समजतात

"हळू आहे? optimize कर / मोठा server घे." अंदाजाने optimize
करणं म्हणजे अंधारात गोळीबार: बहुधा चुकीची जागा, वेळ वाया,
आणि खरा गुन्हेगार तसाच. जाणकार आधी **मोजतो** (कुठे वेळ
जातोय: profiling/observability), मग नेमक्या जागी उपाय. "आधी
मोजा, मग बदला" (Book 4, 5.2 चा error analysis; Book 5,
1.12 चा p99): हा एकच नियम debugging चे 90% वाया-कष्ट
वाचवतो. आणि दुसरा गैरसमज: "एकच कारण असतं." अनेकदा
अनेक कारणं एकत्र (चंदूचे दोन): एक सापडला म्हणून थांबू नका.

## नकाशावर

```
3.1-3.3  race/lock | parallel/GPU | distributed
3.4  केसचा निकाल: मोजा-अंदाज-नको; एकेक संशयित तपासा (algo/
     memory/OS/concurrency); चंदूचे दोन गुन्हेगार (swap +
     वेग-मारक lock), गर्दीत एकत्र; debugging = पद्धतशीर तपास
```

**सूत्रावर:** केस सुटली सूत्राने: "हळू" हा वेळ-जागेच्या चुकीच्या
सौद्याचं लक्षण (इथे: disk-swap ने जागा-चूक, lock ने वेळ-चूक).
आणि तो सौदा **मोजून** सापडला, अंदाजाने नाही: जे मोजता येतं
तेच दुरुस्त करता येतं.

## स्वतः बघा (5 मिनिटं)

कधी काहीतरी (गाडी, तब्येत, नातं) "बिघडलं" तेव्हा तुम्ही अंदाजाने
उपाय केला की तपासून? अंदाजाने बहुधा चुकीचा उपाय, वेळ वाया;
तपासून (नेमकं काय बिघडलं मोजून) नेमका उपाय. चंदूची debugging-
कला जीवनातही तीच: **आधी नेमकं काय, मग उपाय.** पुढच्या
वेळी काहीही "हळू/बिघडलेलं" दिसलं की अंदाजाआधी एक प्रश्न:
"मी हे मोजलंय का?"
