# Chapter 4.4 [DEPTH]: "माझ्या machine वर तर चालत होतं"

(DEPTH chapter. ही ओळ software जगातला सगळ्यात जुना विनोद आहे.
हिच्यामागचं सत्य समजलं की "deploy" आणि "DevOps" सारखे जड शब्द हलके
होतील.)

प्रसंग: engineer ने feature बनवलं, आपल्या laptop वर शंभर वेळा
चालवलं, सगळं perfect. Server वर टाकलं: crash. User च्या phone वर:
रिकामी screen. Engineer ची पहिली ओळ: "माझ्या machine वर तर चालत
होतं..."

तो खोटं बोलत नाहीये. मग चूक कुठे आहे?

Chapter 3.5 मधून विचार करा. Recipe कधीच एकटी चालत नाही: ती OS कडे
मागते, दुसऱ्या recipes ना (libraries) बोलावते, settings वाचते,
files शोधते. म्हणजे recipe च्या भोवती एक पूर्ण **माहोल** आहे
ज्याच्यावर ती टेकलेली आहे:

```
code स्वतः                (हा तर दोन्हीकडे सारखाच होता)
+ OS आणि त्याचं version   (laptop: Windows 11; server: Linux)
+ libraries चे versions   (laptop वर नवे, server वर जुने)
+ settings, passwords     (laptop वर test वाले, server वर खरे)
+ दुसऱ्या services        (laptop वर नकली bank; server वर खरी)
```

Code सारखा, माहोल वेगळा = निकाल वेगळा. "चालत होतं" चं पूर्ण सत्य:
"**माझ्या** माहोलात चालत होतं." या भोवतीच्या पूर्ण दुनियेचं नाव
**environment**.

घरची डाळ आठवा. तुमच्या घरी दरवेळेस perfect बनते. तीच recipe
मावशीच्या घरी बनवा: cooker वेगळा, आच वेगळी, मिठाचा डबा वेगळा. चव
बदलली. Recipe खोटी बोलली नाही; **kitchen** बदललं होतं.

मग इलाज स्वतःच सुचतो: माहोलही code सारखा बनवा. लिहून ठेवा की या
recipe ला काय-काय लागतं (OS, libraries चे exact versions,
settings), आणि अशी व्यवस्था करा की प्रत्येक जागी, laptop पासून
server पर्यंत, **तोच** माहोल बनेल. Recipe सोबत पूर्ण kitchen च
pack करून द्या.

ही व्यवस्था बनली; डब्याचं नाव **container**, सगळ्यात प्रसिद्ध
हत्यार **Docker**. एक डबा ज्यात code + त्याचा माहोल एकत्र बंद
आहे; डबा जिथे उघडेल, आतली दुनिया सारखीच असेल. नाव ship च्या
container वरूनच घेतलं: सामान कुठलंही असो, डबा एकसारखा, म्हणून
प्रत्येक बंदराची crane तो उचलते. McDonald's चं रहस्यही हेच:
त्यांनी recipe नाही, **kitchen** standard केलं, म्हणून प्रत्येक
शहरात चव तीच. आणि code ला laptop वरून खऱ्या server पर्यंत
पोहोचवण्याच्या कामाचं नाव **deploy**; हे सगळं सांभाळणाऱ्या पेशाचं
नाव **DevOps**.

## इथे लोक काय चुकीचं समजतात

"Software = code ची file. File पाठवली, काम संपलं." आता तुम्हाला
माहीत आहे: software = code + माहोल. म्हणून "app बनली, आता live
करणं म्हणजे बस एक button असेल ना" हा founder चा सगळ्यात महाग भ्रम
आहे. Deploy हे स्वतःचं पूर्ण काम आहे: माहोल बनवणं, तपासणं, जुन्या
version वरून नव्यावर विना-थांबा जाणं, चूक झाल्यास परत फिरणं.
Estimate मध्ये याचा वेळ वेगळा विचारा, नाहीतर "झालं" आणि "चालतंय"
मधले आठवडे तुम्हाला surprise करतील.

## MAP वर

रुपयाचा रस्ता: हा त्रास इतका खरा आहे की त्याच्या इलाजाच्या
companies billions च्या आहेत. Docker ने डबा दिला; मग प्रश्न आला
"हजार डबे कोण सांभाळणार" तर Google ने Kubernetes उघडं केलं (open
source: Chapter 3.7 ची चाल, सगळे त्याच्या cloud च्या पद्धतीवर
यावेत म्हणून); आणि cloud companies चा (Part 5) अर्धा business हाच
आहे: "माहोलाची कटकट आम्हाला द्या, भाडं द्या." जिथे प्रत्येक team
चं दुखणं एकसारखं असतं, तिथे platform बनतो, आणि platform जकात वसूल
करतो. दुखणं शोधा; दुकान तिथेच उघडा.

## स्वतः बघा (5 मिनिटं)

Play Store/App Store मध्ये कुठल्याही app चं page उघडा, खाली
"Requires Android 12+" किंवा "Requires iOS 16+" शोधा. हे
environment चं सगळ्यात सरळ रूप आहे: app म्हणते आहे "माझं kitchen
किमान इतकं नवं हवं." आता समजेल जुन्या phone वर नवी app का चालत
नाही: code नाही, माहोल छोटा पडला.

## विचार करा

1. (derivation) दोन मित्र, अगदी सारखा phone model, सारखं app
version. एकाच्या phone वर app रोज crash, दुसऱ्याच्या कधीच नाही.
Code सारखा, phone सारखा. मग काय वेगळं असू शकतं? किमान तीन गोष्टी
मोजा.

> **उत्तर:** माहोल अजूनही वेगळा आहे: (1) OS चं छोटं version/update
> वेगळं असू शकतं, (2) एकाचा storage जवळजवळ full आहे (लिहायला जागा
> नाही = विचित्र crashes), (3) permissions वेगळ्या (एकाने location
> नाकारलं; app चा तो रस्ता कधी test झालाच नव्हता), (4) भाषा/region
> setting वेगळं (तारखेचं रूप वेगळं = चूक), (5) background apps
> आणि battery-saver वेगळे. धडा: "सारखा phone" कधीच सारखा नसतो.
> म्हणून मोठे apps हजारो खऱ्या devices वर test होतात, आणि तरीही
> Chapter 4.1 चा नियम लागू राहतो: कुठली तरी जोडी सुटतेच.
