# Chapter 7.1 [SPINE]: एका user पासून लाखांपर्यंत

तुमचं app चाललं. 100 users: सगळं छान. एका दिवशी कुठल्या celebrity
ने उल्लेख केला, आणि संध्याकाळपर्यंत 100,000 लोक दारात. Server धापा
टाकतो, app "loading..." वर अडकतं, नवे users वैतागून जातात. हा क्षण
प्रत्येक startup च्या स्वप्नात आणि दुःस्वप्नात एकाच वेळेस असतो.

आता design तुम्ही करा. गर्दी दहापट झाली; रस्ते किती?

**पहिला रस्ता: मोठी machine घ्या.** जास्त CPU, जास्त RAM. नाव:
**vertical scaling** (उभं वाढणं). हलवायाची उपमा: दिवाळीत मागणी
दहापट झाली; हलवाई स्वतः दहापट वेगाने काम करायचा प्रयत्न करतो.
सोपं आहे (काहीच बदलावं लागत नाही), पण दोन भिंती आहेत: एक, जगातली
सगळ्यात मोठी machine ही **एक** मर्यादा आहे; तिच्यापुढे रस्ता बंद.
दोन, दुप्पट ताकदीची machine दुप्पट नाही, चौपट महाग असते. आणि
तिसरी, सगळ्यात वाईट: ती **एकच** आहे; ती मेली तर सगळं मेलं.

**दुसरा रस्ता: अनेक machines लावा.** दहा सामान्य servers, प्रत्येक
गर्दीचा दहावा हिस्सा घेतो. नाव: **horizontal scaling** (आडवं
वाढणं). हलवाई आता दहा counters उघडतो, प्रत्येकावर एक माणूस. हाच
खरा खेळ आहे, कारण भिंत नाही: अजून गर्दी? अजून counters. पण दोन नवे
प्रश्न जन्मतात, आणि दोन्हींची उत्तरं तुम्ही आधीच शिकला आहात:

**प्रश्न 1: कुठला ग्राहक कुठल्या counter वर?** दारात एक वाटप
करणारा लागतो: आलेली प्रत्येक विनंती जो मोकळ्या server कडे पाठवतो.
नाव: **load balancer**: मिठाई दुकानाचा token देणारा माणूस, ST
stand चा "platform 4 वर जा" सांगणारा फळा. साधी कल्पना, पण आता
पूर्ण system चं दार हाच आहे.

**प्रश्न 2: state कुठे?** Part 2 आठवा (Chapter 3.6): process ची
state. User ची cart server क्रमांक 3 च्या memory त ठेवली, आणि
पुढची विनंती load balancer ने server 7 कडे पाठवली: cart गायब!
उत्तर Part 4 ने दिलं आहे: state servers वर ठेवायचीच नाही; ती
database/cache मध्ये (सामायिक जागी) ठेवायची, आणि servers
**रिकामे** (stateless) ठेवायचे: कुठलाही server, कुठलीही विनंती,
उत्तर तेच. Counters वरचे कारागीर बदलले तरी चालतं, कारण order ची
वही एकाच गल्ल्यावर आहे.

हे खऱ्या जगात रोज दिसतं: IRCTC tatkal च्या क्षणी, Hotstar world
cup च्या दिवशी हजारो servers उभे केले जातात; match संपला की कमी.
आणि जिथे हे जमलं नाही तिथे काय होतं तेही तुम्ही बघितलं आहे:
concert ची tickets, exam चे forms: "site पडली."

## इथे लोक काय चुकीचं समजतात

"मोठा server घेतला की प्रश्न मिटला." Vertical scaling हे वेदना-
शामक आहे, इलाज नाही: भिंत जवळ येते आणि किंमत उडते. आणि उलटी चूक:
पहिल्या दिवसापासून "crores users साठी" बांधत बसणं: ते Chapter 4.5
चं उलटं पाप आहे: users 50 आणि architecture NASA चं. शहाणा क्रम:
सुरुवात सोपी (एक server ही चालेल), पण **stateless ठेवा**, म्हणजे
गर्दी आली की आडवं वाढणं फक्त "अजून counters" इतकं सोपं राहतं.
तयारी design मध्ये; खर्च गरजेच्या वेळी.

## MAP वर

रुपयाचा रस्ता: scale झेलता येणं हे startup चं जगणं-मरणं आहे:
"viral झालो आणि पडलो" म्हणजे दारात आलेली संधी परत गेली, आणि
संधी क्वचित दोनदा दार वाजवते. म्हणून गुंतवणूकदार विचारतात: "हे
दहापट users झेलेल का?" आणि म्हणूनच cloud (Chapter 7.5) जिंकलं:
"अजून counters" एका click वर मिळू लागले. Level 3 च्या या एका
कौशल्याने Level 2 ची कुठली स्वप्नं जगतात-मरतात हे ठरतं.

## स्वतः बघा (5 मिनिटं)

पुढच्या मोठ्या sale च्या दिवशी (Big Billion Days / Prime Day)
किंवा result च्या दिवशी लक्ष द्या: apps थोडी हळी, कधी रांग, कधी
"try again". आता तुम्हाला **का** ते दिसतं: मागे कुठेतरी counters
कमी पडतायत, load balancer रांगा लावतोय. आणि जेव्हा सगळं गुळगुळीत
चालतं, तेव्हा आता तुम्हाला माहीत आहे: ते आपोआप नाही; कोणीतरी हे
chapter जगून दाखवलं आहे.
