# BOOK 5, PART 1 चा शेवट

## जे तुमच्याकडे आता आहे

```
एक server         तीन कामं (ऐक-विचार-लक्षात ठेव); सोपं पण
                  एकच अपयश-बिंदू; premature scaling टाळा
database/ACID     शिस्तीची वही: अखंड-सुसंगत-एकांत-टिकाऊ;
                  खात्री विकत, वेग विकून; backup तपासलेला हवा
index             अनुक्रमणिका; वाचन जलद, लेखन+जागा विकून;
                  जिथे शोध तिथेच (सगळीकडे नको)
cache             हातासरशी उत्तर; वेग विकत, ताजेपणा विकून;
                  खरा प्रश्न "जुनं कधी फेकायचं"
replication       प्रती; टिकाव+वाचन-वेग विकत, ताजेपणा विकून;
                  ताजं-हवं मुख्याकडे, जुनं-चालेल प्रतीकडे
sharding          तुकडे; लेखन-वाढ विकत, एकत्रित प्रश्न विकून;
                  shard key = भार-भाकीत; शेवटचा उपाय
queue             रांग; धक्का शोषतो; "किमान एकदा" ->
                  idempotency (दोनदा केलं तरी परिणाम एकदाच)
load balancer     वाहतूक-पोलिस; horizontal scaling (अनेक
                  स्वस्त > एक महाग); अट: servers विसराळू
CDN               गिऱ्हाईकाजवळ static; वेग+bill दोन्ही; dynamic
                  मुळाशी
CAP               फूट अटळ; मग C (अचूक-थांबा) की A (उत्तर-जुनं);
                  पैसे->C, like->A
अपयश-सज्जता       timeout + retry(थांबत) + circuit breaker;
                  एका भागाचं अपयश पसरू देऊ नका
observability     logs+metrics+traces; सरासरी खोटं, टोक(p99) खरं
चार प्रलय         S3/Knight/FB/CrowdStrike: बिघाड लहान, पसरला
                  म्हणून प्रलय; canary + स्वतंत्र बचाव
cloud-bill        egress-सापळा + lock-in; bill रोज बघा
```

## स्वतःची परीक्षा (4 प्रश्न, बोलून; उत्तरं खाली)

**1.** App हळू झालं. पहिलं निदान "मोठा server घेऊ" का नाही?

> कारण 90% हळूपणा रचनेत असतो, ताकदीत नाही: गहाळ index,
> गहाळ cache, वाचनं मुख्यावर (replicas कडे वळवा). पैसे
> ओतण्याआधी नजर. (1.3, 1.4, 1.5)

**2.** Queue वापरता तर idempotency का हवीच?

> queue ची हमी "किमान एकदा" = तेच काम दोनदा येऊ शकतं;
> idempotency शिवाय दुहेरी payment/ऑर्डर. (1.7)

**3.** पैशाच्या शिल्लकीला CAP मध्ये C की A, आणि का?

> C (सुसंगती): फूट पडली तर "थांबा" चालेल, पण चुकीचा आकडा
> नाही. like-count ला उलट (A). (1.10)

**4.** System निरोगी आहे हे सरासरी-वेळेवरून का ठरवू नये?

> सरासरी बहुसंख्य-सुखींत अल्पसंख्य-दुःखी लपवते; धंदा टोकाने
> (p99) मोजला जातो: तोच गिऱ्हाईक बोलतो-सोडतो. (1.12)

## पुढच्या भागाची चाहूल

आरतीचे दोन मोठे निर्णय Part 2 उघडतात: **app चे तुकडे
करावेत का** (monolith vs microservices) आणि **कडक database
की सैल** (SQL vs NoSQL). Part 2 त हे मोठे रचना-वाद, data
modeling, API-रचना, आणि search: सगळं Part 1 च्याच एका
सूत्राने: **सौदा बघा, fashion नको.**
