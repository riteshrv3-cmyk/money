# Chapter 1.15 [SPINE]: आरतीचं पूर्ण चित्र

विभागाचा कळस: सगळे तुकडे एका चित्रात. आरती मागे वळून
बघते: एक laptop पासून इथवरचा प्रवास, आणि प्रत्येक भिंतीचा
सौदा. हे चित्र पाठ करा; कुठलंही मोठं app याच आकाराचं असतं.

**एका विनंतीचा आजचा प्रवास (सुरुवातीच्या सहा पायऱ्या, आता
पूर्ण वाढलेल्या):**

```
गिऱ्हाईकाचा फोन
   |
   v
CDN            (जवळचं static: फोटो, design: जवळून, जलद)
   |
   v
Load Balancer  (वाहतूक-पोलिस: मोकळ्या server कडे, मेलेले टाळून)
   |
   v
अनेक Servers   (विसराळू/stateless; horizontal scaling;
   |            प्रत्येक timeout+retry+circuit breaker ने सज्ज)
   |--> Cache         (वारंवारचं उत्तर हातासरशी; "जुनं कधी फेकायचं")
   |--> Queue         (जड/धीमी कामं रांगेत; idempotent)
   |
   v
Database
   Primary (लेखन) --replication--> Replicas (वाचन; थोडं जुनं)
   मोठं झालं तर --> Shards (तुकडे; भार वाटला)
   प्रत्येक शोध <-- Index (अनुक्रमणिका; जिथे शोध तिथेच)

आणि या सगळ्यावर:
   Observability (logs+metrics+traces; टोक/p99 बघा)
   अपयश-सज्जता   (एक भाग पडला तरी पसरू नये)
   Bill-भान      (egress, auto-scale रोज मोजा)
```

**नऊ सौद्यांचा सारांश (हीच खरी शिकवण):**

```
एक-यंत्र vs अनेक    सोपेपणा <-> वाढ+टिकाव
ACID               वेग <-> खात्री
index              लेखन+जागा <-> वाचन-वेग
cache / CDN        ताजेपणा <-> वेग
replication        ताजेपणाची-खात्री <-> टिकाव+वाचन-वेग
sharding           सोपे-प्रश्न <-> लेखन-वाढ
queue              "लगेच झालं" <-> लवचिकता (+idempotency)
CAP (फूट-क्षणी)     C (अचूक-पण-थांबा) <-> A (उत्तर-पण-जुनं)
cloud              पैसा+स्वातंत्र्य <-> सोय+वेग
```

**आणि "भिंत येण्याआधी दिसणं" ची नजर (आरतीचा खरा प्रश्न):**
आता आरती नवं app बांधताना प्रत्येक भिंतीला आपटायची वाट
बघत नाही; ती **आधीच** विचारते: "ही माहिती वाढणार का
(index)? वारंवार तेच विचारलं जाणार का (cache)? एक यंत्र
पडलं तर (replication+load balancer)? कुठलं काम धीमं आहे
(queue)? फूट पडली तर C की A?" **पण: एकही गोष्ट गरजेआधी
बांधायची नाही.** नजर म्हणजे "भिंत ओळखणं", घाई म्हणजे "भिंत
नसताना भिंत बांधणं" (premature scaling: 1.1, 1.6 चा इशारा).
प्रौढ engineer भिंत **येताना दिसते** पण **आल्यावरच** बांधतो:
आधी नाही (उगाच गुंतागुंत), खूप उशिरा नाही (crash).

**सर्वात मोठा धडा, एका ओळीत:** आरतीने कुठलीही "जादूई
भारी रचना" शिकली नाही; तिने **सौदे बघायला** शिकलं. "सगळ्यात
चांगलं software" असं काही नसतं; फक्त "या गर्दीला, या माहितीला,
या क्षणी योग्य" असतं. आणि उद्या गर्दी बदलली की योग्य रचनाही
बदलेल. **रचना ही स्थिर गोष्ट नाही; ती सतत बदलणाऱ्या सौद्यांची
जिवंत निवड आहे.** हीच Part 1 ची कमाई, आणि Part 2 चा पाया:
कारण Part 2 त आपण हे सौदे **मोठ्या रचना-निर्णयांना** लावू:
SQL की NoSQL, एक-मोठं-app की अनेक-लहान-सेवा.

## महाग चूक

"आता मला सगळं येतं, पुढच्या app मध्ये हे सगळं आधीच टाकतो."
Part 1 ची शिकवण **उलटी** आहे: तुम्हाला सगळे **सौदे** कळले,
म्हणजे आता तुम्ही प्रत्येक गोष्ट **गरजेपुरती** टाकाल. ज्ञानाचा
उपयोग "सगळं आधीच बांधणं" नाही, तर **"कधी काय लागेल हे
ओळखून, तेव्हाच बांधणं."** नवशिक्याची चूक: काहीच न जाणणं.
अर्धवट-शिकलेल्याची चूक: सगळं आधीच बांधणं. जाणकाराची नजर:
भिंत ओळखणं, आणि तिची वाट बघणं.

## नकाशावर

```
Part 1 पूर्ण: प्रवासाचा पूर्ण नकाशा
CDN -> LB -> stateless servers (+cache, +queue) -> DB
(primary/replicas/shards, +index); त्यावर observability +
अपयश-सज्जता + bill-भान. नऊ सौदे. नजर = भिंत आधी दिसणं,
पण गरजेआधी न बांधणं.
```

**सूत्रावर:** पूर्ण Part 1 एका वाक्यात: **मोठेपणा फुकट नसतो;
प्रत्येक भिंतीवर काहीतरी विकून काहीतरी घ्यावं लागतं, आणि
जाणकार तो सौदा जाणून करतो.** हेच अभियांत्रिकीचं सौंदर्य.

## स्वतः बघा (5 मिनिटं)

तुमचं आवडतं मोठं app (Zomato, WhatsApp, कुठलंही) घ्या
आणि वरचं "पूर्ण चित्र" त्याला लावून बघा: त्यात CDN असेल
(images भरभर), load balancer (कधीच "एकच server पडला"
दिसत नाही), cache (काही गोष्टी झटकन, refresh वर बदलतात),
queue ("processing, थांबा"). तुम्ही आता app च्या मागचं जाळं
"वाचू" शकता: हीच Part 1 ची कमाई.

## विचार करा

Part 1 संपला. आरतीला आता एक मोठा निर्णय घ्यायचाय: तिचं
अख्खं app एकाच मोठ्या code मध्ये आहे (सोपं होतं सुरुवातीला).
आता 30 engineers काम करतायत आणि एकमेकांच्या पायात येतायत:
एकाने बदल केला की दुसऱ्याचं मोडतं. "app चे तुकडे करावेत
का? प्रत्येक टीमला स्वतःचा तुकडा? की एकत्रच बरं?" आणि
दुसरा प्रश्न: "माझी काही माहिती ACID-कडक database मध्ये
आहे, पण like-count सारखी सैल माहिती त्याच कडक जागी
कशाला? वेगळी, सैल database वापरू का?"

> हे दोन प्रश्न Part 2 चे दोन सर्वात मोठे वाद आहेत: monolith
> vs microservices, आणि SQL vs NoSQL. आणि दोन्हींचं उत्तर
> Part 1 च्या एकाच सूत्रात आहे: **सौदा बघा, fashion नको.**
> Part 2, पान पहिलं: रचनेचे मोठे निर्णय.
