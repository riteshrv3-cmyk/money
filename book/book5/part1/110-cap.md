# Chapter 1.10 [SPINE]: CAP: तीनातले दोनच मिळतात

Replication पासून (1.5) एक प्रश्न घोंगावतोय: प्रती एकसारख्या
कशा राहणार? आता त्याचं मूळ उत्तर: आणि ते एका कठोर,
सुंदर नियमात आहे: **CAP theorem.** हा नियम एकदा समजला
की distributed systems मधले अर्धे वाद संपतात.

**तीन इच्छा.** अनेक यंत्रांच्या (distributed) system कडून
आपल्याला तीन गोष्टी हव्या असतात:

```
C  Consistency (सुसंगती): कुठल्याही यंत्राला विचारा, तेच,
   ताजं उत्तर. रमेशची ऑर्डर सगळ्या प्रतींवर लगेच सारखी.
A  Availability (उपलब्धता): विचारलं की उत्तर मिळतंच,
   कधीच "थांब, माहीत नाही" नाही.
P  Partition tolerance (फूट-सहनशीलता): दोन यंत्रांमधला
   संपर्क तुटला (network फुटली) तरी system चालूच राहते.
```

**कठोर सत्य: तिन्ही एकदम मिळत नाहीत.** आणि गंमत अशी की
अनेक-यंत्रांच्या जगात **P (फूट) टाळताच येत नाही**: तारा तुटतात,
network मध्ये अडथळे येतात: कधीतरी दोन यंत्रांचा संपर्क तुटणारच.
म्हणून खरा निर्णय दोनातलाच उरतो: **फूट पडली त्या क्षणी,
C निवडायचं की A?**

दोन कारकुनांची उपमा (हीच पूर्ण CAP आहे): दोन गावांतल्या
दोन कारकुनांकडे एकाच खात्याची वही आहे, आणि त्यांच्यातला
फोन बंद पडलाय (partition). आता गिऱ्हाईक एका कारकुनाकडे
येऊन विचारतो "माझी शिल्लक?" कारकुनापुढे दोनच पर्याय:

- **A निवड (उपलब्धता):** "ही घ्या शिल्लक" (स्वतःच्या वहीतली):
  उत्तर मिळालं, पण दुसऱ्या गावात कदाचित बदल झाला असेल,
  म्हणजे हे उत्तर **कदाचित जुनं** (C सोडलं).
- **C निवड (सुसंगती):** "फोन येईपर्यंत थांबा, खात्री करून
  सांगतो": उत्तर **अचूकच** असेल, पण तोवर गिऱ्हाईक **ताटकळला**
  (A सोडलं).

एकच "बरोबर" उत्तर नाही: **माहितीच्या स्वभावावर** ठरतं. आणि
इथे या पुस्तकाचं सूत्र शिखरावर: CAP म्हणजे "काय विकून काय
घ्यायचं" चा सर्वात शुद्ध नियम.

**कुठे काय: आरतीचे निर्णय.** (1) **पैसे/शिल्लक: C निवडा.**
"थोडं थांबा" चालेल, पण चुकीची शिल्लक नको (दुहेरी खर्च,
कायदेशीर घोळ). बँका इथे नेहमी C: फूट पडली तर व्यवहार
थांबवतात, चुकीचा आकडा दाखवत नाहीत. (2) **like-count / "किती
जणांनी बघितलं" / दुकानाची जुनी यादी: A निवडा.** उत्तर आलंच
पाहिजे (गिऱ्हाईक थांबणार नाही); 5 सेकंद जुना like-count चालतो.
Social media इथे नेहमी A. **एकाच app मध्ये, माहितीगणिक
वेगळी निवड**: हीच प्रौढ रचना (replication chapter चा "ताजं-हवं
की जुनं-चालेल" तोच धागा, आता नियमात बांधलेला).

## महाग चूक

"आम्हाला तिन्ही हवेत: नेहमी ताजं, नेहमी उपलब्ध, आणि फूट
सहन करणारं." हे मागणं म्हणजे भौतिकशास्त्राशी भांडण: तिन्ही
एकदम अशक्य आहेत (सिद्ध झालेलं). जो engineer "तिन्ही देतो"
असं म्हणतो तो एकतर खोटं बोलतोय किंवा त्याला अजून फूट
भेटलेली नाही (आणि ती भेटणारच). नवखा तिन्हींची अपेक्षा करतो;
जाणकार **आधीच ठरवतो**: "या माहितीला फूट पडली तर मी C
निवडेन की A": आणि तो निर्णय माहितीच्या स्वभावावर, कोड
लिहिण्याआधी.

## नकाशावर

```
1.1-1.9  यंत्र...CDN (नऊ भिंती, नऊ सौदे)
1.10 CAP: फूट अटळ; मग C की A? तीनातले दोनच; पैसे->C
     (थांबा पण अचूक), like->A (जुनं पण उत्तर मिळो)
```

**सूत्रावर:** CAP हा सूत्राचा गाभा-नियम: distributed जगात
"सगळं एकदम" असं काहीच नसतं; प्रत्येक क्षणी एक विकून एक
घ्यावंच लागतं. ही निवड टाळता येत नाही; फक्त **जाणून** किंवा
**नकळत** करता येते. जाणकार जाणून करतो.

## स्वतः बघा (5 मिनिटं)

दोन अनुभव आठवा: (1) बँकेत/UPI त कधी "system busy,
थोड्या वेळाने प्रयत्न करा" आलंय? ती बँकेची **C निवड** होती:
अचूकतेसाठी उपलब्धता सोडली. (2) Social media वर like-count
कधी मागे-पुढे झालेला दिसला? ती **A निवड**: उत्तर देत राहायला
अचूकता सोडली. एकच तत्त्व, दोन विरुद्ध निर्णय: माहितीच्या
स्वभावाने.

## विचार करा

आरतीला आता एक विचित्र गोष्ट जाणवली: तिच्या मोठ्या system
मध्ये छोटे-छोटे बिघाड **सतत** होत असतात: एखादा server क्षणभर
अडतो, एखादी सेवा उशिरा उत्तर देते: पण गिऱ्हाईकाला कळतही
नाही. पण कधीकधी एक छोटा बिघाड **पसरतो** आणि सगळं
कोसळतं (1.9 चा payment-अडथळा). आरती विचारते: "छोटे बिघाड
तर होणारच. मग ते पसरून सर्वनाश होऊ नये, एका जागी थांबावेत:
याची रचना कशी करायची?"

> हाच distributed systems मधला सर्वात प्रौढ प्रश्न: **अपयश
> गृहीत धरून, ते मर्यादित ठेवणारी रचना.** Timeouts, retries,
> आणि "circuit breaker": एका बिघाडाला साखळी होऊ न देणारी
> यंत्रणा. पुढची भिंत.
