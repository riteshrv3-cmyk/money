# Chapter 1.4 [SPINE]: Cache: हातासरशी उत्तर, आणि त्याचं दुखणं

Cache ही software मधली सगळ्यात मोठी वेग-देणारी युक्ती आहे,
आणि तिच्याबद्दल एक जगप्रसिद्ध विनोद आहे: **"Computer science
मध्ये फक्त दोनच अवघड गोष्टी आहेत: cache मधून गोष्ट कधी
काढायची, आणि गोष्टींना नावं देणं."** का अवघड, ते आरतीच्या
दिवाळीत दिसेल.

**Cache म्हणजे काय.** दुकानदाराची उपमा: रोज विचारला जाणारा
भाव (साखर, तेल) दुकानदार गोदामात जाऊन बघत नाही; तो
गल्ल्याजवळ एका कागदावर लिहून ठेवतो: **हातासरशी.** Cache
तेच: वारंवार लागणारं उत्तर database मध्ये न जाता एका **जलद,
जवळच्या** जागी (memory त) ठेवायचं. आरती आजचे भाव, लोकप्रिय
दुकानांच्या याद्या cache मध्ये ठेवते: हजारो लोक विचारले तरी
database ला त्रास नाही, उत्तर गल्ल्याच्या कागदावरून. दिवाळीचा
भार पेलला. Cache मुळे वाचनं 10-100 पट जलद-स्वस्त होऊ
शकतात: म्हणून प्रत्येक मोठं app cache वापरतं.

**पण इथे सूत्राचं सगळ्यात कपटी रूप: cache = वेग विकत,
ताजेपणा विकून.** गल्ल्यावरचा कागद जुना झाला तर? साखरेचा
भाव गोदामात बदलला पण कागदावर जुनाच राहिला: दुकानदार
चुकीचा भाव सांगतो. Cache मधली माहिती आणि खरी (database
मधली) माहिती **वेगळी पडणं**: याला **stale cache** (शिळं
cache) म्हणतात, आणि हेच ते "कधी काढायची" चं दुखणं. आरतीच्या
app मध्ये हे घडलं: एका दुकानाने साखर संपली म्हणून काढून
टाकली, पण cache मध्ये "उपलब्ध" राहिली: रमेशने ऑर्डर केली,
दुकानात गेल्यावर "नाही" म्हणाले. एक शिळ्या-cache ची चूक =
एक नाराज गिऱ्हाईक.

**म्हणून cache चा खरा प्रश्न: जुनं कधी फेकायचं (invalidation).**
तीन ढोबळ रीती (प्रत्येकीला सौदा): (1) **वेळ ठरवा (TTL):**
"हा भाव 5 मिनिटं ताजा माना, मग नव्याने आणा": सोपं, पण 5
मिनिटं जुनी माहिती चालेल तरच. (2) **बदललं की फेका:** भाव
database मध्ये बदलला की cache मधून लगेच काढा: ताजं, पण
गुंतागुंतीचं (प्रत्येक बदलाला cache-ला कळवावं लागतं). (3)
**जागा संपली की जुनं-न-वापरलेलं फेका:** cache भरली की सगळ्यात
कमी वापरलेलं बाहेर. निवड कशावर? **"किती जुनी माहिती चालेल"**
यावर: भावाला काही मिनिटं चालतं; शिल्लक/पैसे यांना **शून्य**
शिळेपणा (तिथे cache टाळाच, किंवा अति-कडक).

**नवख्याचा धडा (आरतीने घेतला):** cache हे "app हळू झालं
की टाकायचं मलम" नाही. **आधी विचारा: ही माहिती किती वेळ
जुनी चालेल?** "अजिबात नाही" (पैसे) तर cache नको; "काही
मिनिटं चालेल" (भाव, याद्या) तर cache सोनं. हा एक प्रश्न न
विचारता cache टाकणारे engineers शिळ्या-माहितीचे bugs वर्षानुवर्षं
शोधत बसतात: कारण bug **कधीतरीच** दिसतो (cache ताजं
असताना नाही, शिळं असताना), म्हणून पकडणं कठीण.

## महाग चूक

"Cache टाकलं, app जलद झालं, काम फत्ते." Cache टाकणं सोपं;
**कधी काढायचं** ठरवणं अवघड: आणि तेच न ठरवता cache
टाकणारे सगळ्यात कपटी bug विकत घेतात: गिऱ्हाईकाला चुकीचा
भाव/शिल्लक, जो तुमच्या testing मध्ये कधीच दिसत नाही (कारण
तुमचं cache ताजं असतं). Stale cache चे bugs हे software मधले
सर्वात जास्त वेळ लपून राहणारे bugs आहेत. Cache टाकताना
पहिला प्रश्न "जलद होईल का" नाही, **"जुनं कधी, कसं फेकायचं"**
हा आहे.

## नकाशावर

```
1.1  एक यंत्र, तीन कामं    1.2  ACID: खात्री विकत
1.3  index: वाचन जलद, लेखन विकून
1.4  cache: वेग विकत, ताजेपणा विकून; खरा प्रश्न "जुनं
     कधी फेकायचं"; "किती जुनं चालेल?" आधी विचारा
```

**सूत्रावर:** cache हा सगळ्यात मोहक सौदा (प्रचंड वेग) आणि
सगळ्यात लपलेली किंमत (शिळेपणा). जो "किती जुनं चालेल"
आधी विचारतो तो cache चा मालक; जो नुसतं वेगासाठी टाकतो
तो cache चा गुलाम.

## स्वतः बघा (5 मिनिटं)

तुमच्या फोनवर कुठलंही app उघडा, मग "refresh"/खाली-ओढून-
ताजं-करा. जे नवं दिसतं ते cache मध्ये जुनं होतं: तुम्ही ते
आत्ता फेकलंत (manual invalidation!). कुठली माहिती refresh
शिवाय जुनी राहते (cache), कुठली नेहमी ताजी येते (no cache):
याचा अंदाज घ्या. App-designers नी कुठे "किती जुनं चालेल"
ठरवलंय ते तुम्हाला दिसेल.

## विचार करा

आरतीचं app आता चांगलं चाललंय. पण एका दुपारी तिचा एकुलता
एक server (cloud मधला) बंद पडला: hardware बिघाड. **पूर्ण
app बंद**, दोन तास. गिऱ्हाईकं, दुकानं, सगळे अडकले. आरती
हादरली: "एकाच यंत्रावर पूर्ण धंदा: हे धोक्याचं आहे. पण एकच
database आहे: तिच्या दोन प्रती कशा ठेवणार? दोन्ही एकसारख्या
कशा राहणार?"

> आरती आत्ता 1.1 चा "एकच अपयश-बिंदू" प्रत्यक्ष भोगतेय.
> उत्तर: database ची प्रत ठेवायची: याला replication म्हणतात.
> पण "दोन्ही एकसारख्या कशा राहणार" हा तिचा प्रश्न या पुस्तकातला
> सगळ्यात खोल प्रश्नांपैकी एक आहे: पुढची भिंत.
