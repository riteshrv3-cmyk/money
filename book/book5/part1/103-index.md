# Chapter 1.3 [SPINE]: Index: गोदामाची वही

आरतीचं app हळू का झालं? उत्तर एका जुन्या कारकुनी युक्तीत
आहे, आणि ती युक्ती समजली की database चा अर्धा वेग-गूढ
संपतो.

**पूर्ण वही चाळणं वि. अनुक्रमणिका.** समजा एका जाड पुस्तकात
"साखर" शब्द कुठे आहे शोधायचंय. दोन मार्ग: (1) पहिल्या पानापासून
प्रत्येक ओळ वाचत जाणं: 500 पानी पुस्तकाला वेळ लागेल, पण
चालेल; 5 लाख पानी पुस्तकाला **आयुष्य** लागेल. (2) मागच्या
**अनुक्रमणिकेत** "साखर" बघणं: "पान 213": थेट तिथे. Database
ची डिफॉल्ट पद्धत पहिली आहे (full scan: पूर्ण table चाळणं).
आरतीच्या 500 ऑर्डरला ते चालत होतं; 5 लाखांना कोसळलं.
**Index म्हणजे database ची अनुक्रमणिका.**

**Index कसं काम करतं.** आरती database ला सांगते: "रमेशच्या
फोन-नंबरवर मी वारंवार शोधते: त्याची अनुक्रमणिका बनव."
Database एक वेगळी, **क्रमाने लावलेली** यादी ठेवते: फोन-नंबर ->
"ती नोंद इथे आहे." आता शोध पूर्ण-चाळणीचा नसतो; अनुक्रमणिकेतला
उडी-मारत शोध (5 लाखांत ~19 उड्यांत सापडतं: half-half कापत:
Book 6 चा binary search इथे कामाला येईल). 8 सेकंदांचं काम
काही milliseconds वर. आरतीचं app पुन्हा भुर्रकन.

**पण सूत्र इथेही हजर: index ची तिहेरी किंमत.** फुकट वेग
नाहीच: (1) **जागा:** अनुक्रमणिका ही वेगळी यादी: database
मोठी होते (पुस्तकाच्या मागची 50 पानी index पुस्तक जाड करते).
(2) **लिहिण्याचा वेग:** आता प्रत्येक नव्या ऑर्डरला **दोन**
जागी लिहावं लागतं: मूळ नोंद आणि अनुक्रमणिका (नवा शब्द
आला की index पुस्तकातही भर घालावी लागते). म्हणजे index
वाचन जलद करते पण लेखन हळू. (3) **सांभाळ:** प्रत्येक index
राखावा लागतो. निष्कर्ष: **index = वाचन-वेग विकत, लेखन-वेग
+ जागा विकून.**

**आणि इथे नवख्याची खरी परीक्षा:** "मग सगळ्या स्तंभांवर
index टाकू, सगळं जलद!" चूक. वाचनाला जलद, पण **प्रत्येक**
लेखन तेवढ्याच index मध्ये भर घालत बसतं: 15 index असलेली
table मध्ये एक ऑर्डर लिहायला 15 अनुक्रमणिका update: लेखन
कासवगती. Top engineer index टाकतो **जिथे वारंवार शोध होतो
तिथेच**: रमेशचा नंबर, ऑर्डरची तारीख: हो; क्वचित शोधले जाणारे
स्तंभ: नको. **कुठे index, कुठे नाही: हा नजरेचा निर्णय आहे,
आणि तो सौदा बघण्यातून येतो.**

## महाग चूक

"App हळू आहे = मोठा server घेऊ (जास्त पैसे)." आरतीने जवळपास
हीच चूक केली: हळूपणा बघून महागडा server भाड्याने घ्यायला
निघाली. पण खरी अडचण server ची ताकद नव्हती, **गहाळ index**
होती: एका ओळीच्या index ने 10x महागड्या server पेक्षा जास्त
वेग दिला, फुकट. **हळूपणाचं पहिलं निदान "मोठा server" नसून
"कुठली शोध-रचना" हे असतं.** पैसे ओतण्याआधी नजर टाका:
software मधल्या 90% हळूपणाचं मूळ रचनेत असतं, ताकदीत नाही.

## नकाशावर

```
1.1  एक यंत्र, तीन कामं; एकच अपयश-बिंदू
1.2  database = शिस्तीची वही (ACID); खात्री विकत, वेग विकून
1.3  index = अनुक्रमणिका; वाचन जलद, लेखन+जागा विकून;
     जिथे शोध तिथेच
```

**सूत्रावर:** index हा वाचन-वि.-लेखन चा शुद्ध सौदा: तुमचं app
जास्त काय करतं (वाचतं की लिहितं) यावर निर्णय. सौदा न बघता
"सगळीकडे index" म्हणणारा नवखा; "इथे वाचन जास्त म्हणून
index" म्हणणारा जाणकार.

## स्वतः बघा (5 मिनिटं)

कुठलंही पाठ्यपुस्तक उघडा आणि मागची अनुक्रमणिका/index बघा.
एक शब्द निवडा, index वापरून शोधा (2 सेकंद), मग तोच शब्द
पहिल्या पानापासून चाळत शोधायचा कल्पना करा (मिनिटं). हाच
फरक database मध्ये milliseconds वि. सेकंद. आणि लक्षात घ्या:
त्या index पानांनी पुस्तक जाड केलंय: तीच जागेची किंमत.

## विचार करा

आरतीचं app आणखी वाढलं: दिवाळी आली, एका दिवसात 50,000
ऑर्डर. Index असूनही database धापा टाकू लागली: कारण हजारो
लोक **एकाच वेळी** तीच लोकप्रिय माहिती (आजचे भाव, सणाच्या
ऑफर) पुन्हा-पुन्हा विचारत होते. Database प्रत्येक वेळी तीच
गोष्ट नव्याने शोधून देत होती. आरती विचारते: "एकच उत्तर
हजार वेळा तेच असेल, तर दर वेळी नव्याने का शोधायचं?"

> म्हणजे cache: आणि ती software मधली सगळ्यात शक्तिशाली,
> आणि सगळ्यात **धोकादायक** युक्ती आहे. पुढची भिंत.
