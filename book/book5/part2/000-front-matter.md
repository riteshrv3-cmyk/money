# THE BLUEPRINT

## Book 5, Part 2: रचनेचे निर्णय

**मागच्या भागाचा शेवट:** आरतीचे दोन मोठे निर्णय टेबलावर:
app चे तुकडे करावेत का, आणि कडक database की सैल. हा भाग
अशा **मोठ्या रचना-निर्णयां**चा आहे: जिथे "भारी tech" चा मोह
सर्वात जास्त, आणि सूत्र सर्वात जास्त उपयोगी.

## सूत्र (पुन्हा)

```
मोठेपणा फुकट नसतो.
प्रत्येक रचना-निर्णय म्हणजे काहीतरी विकून काहीतरी विकत घेणं.
Trade-off न दिसणं हीच खरी चूक. (आणि: fashion नको, सौदा बघा.)
```

## Part 1 ची उजळणी: 4 प्रश्न (बोलून; उत्तरं खाली)

**1.** App हळू: पहिलं निदान काय, "मोठा server" का नाही?

> रचना: गहाळ index/cache/replica. 90% हळूपणा रचनेत,
> ताकदीत नाही. (1.3-1.5)

**2.** Cache/CDN चा खरा अवघड प्रश्न?

> "जुनं कधी फेकायचं" (invalidation); वेग विकत, ताजेपणा
> विकून. (1.4, 1.9)

**3.** पैशाला CAP मध्ये C की A?

> C: फूट पडली तर थांबा, पण चुकीचा आकडा नाही. (1.10)

**4.** System-आरोग्य सरासरीने का नाही?

> टोक (p99) खरं; सरासरी अल्पसंख्य-दुःखी लपवते. (1.12)

## या भागात काय

Data कशी रचायची, SQL-vs-NoSQL चा गाजलेला वाद, database
आतून कशी शोधते-लिहिते, API म्हणजे करार, monolith-vs-
microservices (आणि Amazon Prime Video ची उलटी गोष्ट),
search कशी चालते, real-time (WhatsApp), आणि चालत्या
system चं चाक बदलणं (migrations). प्रत्येक निर्णयाला तेच
सूत्र: सौदा बघा, fashion नको.
