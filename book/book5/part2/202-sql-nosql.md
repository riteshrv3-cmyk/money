# Chapter 2.2 [SPINE]: SQL vs NoSQL: गाजलेला वाद [दोन्ही बाजू]

Software मधला सर्वात गाजलेला, आणि सर्वात गैरसमजलेला वाद.
आरतीच्या प्रश्नातून तो नीट उलगडू: आणि नेहमीप्रमाणे, उत्तर
"कुठलं भारी" नसून "कधी कुठलं" असेल.

**दोन घराणी.** (1) **SQL / relational** (PostgreSQL, MySQL):
माहिती **ठरलेल्या रकान्यांच्या टेबलांत**, नाती जोडलेली (2.1),
आणि ACID ची कडक शिस्त (1.2). सरकारी फॉर्मची उपमा: प्रत्येक
रकाना ठरलेला, शिस्त कडक, चूक होत नाही, पण साचा बदलायला
अर्ज-परवानग्या. (2) **NoSQL** (MongoDB, Cassandra, Redis
वगैरे: एक नाव नाही, अनेक प्रकार): माहिती **सैल, लवचिक**
रूपात (प्रत्येक नोंद वेगळ्या आकाराची चालते), प्रचंड आकाराला-
वेगाला सोयीची, पण कडक शिस्त सैल. कोऱ्या वहीची उपमा: काहीही,
कसंही लिहा, वेगवान, पण शिस्त तुमच्यावर.

**खरा फरक एका ओळीत:** SQL **शिस्त-आणि-नाती** देतं (शुद्धता,
गुंतागुंतीचे प्रश्न सोपे), वेग-लवचिकता विकून; NoSQL **आकार-
आणि-वेग** देतं, शिस्त-नाती विकून. हा तोच जुना ACID-सौदा
(1.2), आता database-निवडीत. आरतीचं उत्तर आता स्पष्ट: **ऑर्डर-
पैसे-शिल्लक (नाती, शुद्धता हवी): SQL; click-log, बघितलेली-
दुकानं (प्रचंड, सैल, वेग हवा): NoSQL.** एकाच app मध्ये दोन्ही:
माहितीच्या स्वभावानुसार. याला "polyglot persistence" म्हणतात:
अनेक database-भाषा एकत्र.

**आणि आता 2026 चा कडू निकाल (हाच contested-गाभा):**

```
NoSQL-उत्साहाची लाट (2010 च्या दशकात): "SQL जुनं, NoSQL
   सगळीकडे वापरा, तेच भविष्य!"
प्रत्यक्ष अनुभव (आजवरचा): बहुतेकांना NoSQL ची गरज नव्हती;
   त्यांनी नाती (joins), शिस्त (ACID) गमावली आणि नंतर ती
   हाताने, code मध्ये, वाईट रीतीने पुन्हा बांधावी लागली.
2026 ची स्थिती: PostgreSQL (SQL) हे developers मध्ये सलग
   सर्वात लोकप्रिय database (Stack Overflow पाहणी). आणि
   गंमत: आधुनिक SQL आता NoSQL ची लवचिकताही (JSON रकाने)
   देतं. "SQL मेलं" ही भविष्यवाणी उलटली.
निकाल: NoSQL चुकीचं नाही; तो **विशिष्ट** गरजांसाठी (प्रचंड
   आकार, सैल-रचना, अति-वेग) उत्तम. पण **डिफॉल्ट** SQL असावं;
   NoSQL तेव्हा जेव्हा SQL खरंच कमी पडतं, fashion म्हणून नाही.
```

**निवडीची कसोटी (छापून ठेवा):** (1) माहितीला **नाती + शुद्धता**
लागतात का (पैसे, ऑर्डर, नोंदी)? -> SQL. (2) माहिती **प्रचंड,
सैल-आकाराची, अति-वेगवान** आहे आणि नाती कमी (logs, sensor-
data, cache)? -> NoSQL. (3) **शंका असेल तर SQL**: कारण
नाती नंतर सोडता येतात, पण नसताना पुन्हा बांधणं महाग.

## महाग चूक

"मोठं, आधुनिक app म्हणजे NoSQL; SQL जुन्या लोकांचं." हा
fashion-निर्णय हजारो startups ला महागात पडला: त्यांनी सुरुवातीलाच
NoSQL निवडलं (कारण "cool"), मग कळलं की त्यांना ऑर्डर-
गिऱ्हाईक-payment मधली नाती हवीच होती (जी SQL फुकट देतं),
आणि ती त्यांनी code मध्ये हाताने, buggy रीतीने बांधली. **Database
ची निवड "काय cool आहे" वर नाही, "माझ्या माहितीला काय
लागतं" वर.** Fashion आणि सौदा वेगळे करणं: हीच या chapter
ची, आणि पूर्ण Part 2 ची, खरी परीक्षा.


चा मोह विरुद्ध "माझ्या माहितीचा सौदा." जो सौदा बघतो तो
बरोबर निवडतो; जो fashion बघतो तो दोनदा बांधतो.

## स्वतः बघा (5 मिनिटं)

तुमच्या ओळखीच्या माहितीचे दोन प्रकार शोधा: एक जिथे **अचूकता
आणि नाती** महत्त्वाची (बँक-खातं, विद्यार्थ्यांचे गुण), एक जिथे
**प्रचंड आकार आणि वेग** पण अचूकता दुय्यम (कोणी काय बघितलं,
किती वेळ). पहिल्याला SQL, दुसऱ्याला NoSQL: का, ते स्वतःला
समजावा. ही जोडी ओळखता येणं = database-नजर.
