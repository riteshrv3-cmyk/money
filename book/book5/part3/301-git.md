# Chapter 3.1 [SPINE]: Git: इतिहास-यंत्र आणि Review-संस्कृती

Elite शिस्तीचा पाया एका साध्या पण क्रांतिकारी साधनात आहे:
**git.** आरतीला 30 engineers सोबत काम करायचंय; त्या सगळ्यांचं
code एकत्र, चुका न होता, कसं जमवायचं? git चं उत्तर दोन
भागांत: इतिहास-यंत्र, आणि review-संस्कृती.

**भाग 1: git = time-machine.** Book 4 त हे थोडं भेटलं (4.5);
आता पूर्ण. git प्रत्येक बदलाची **नोंद** ठेवतं: कोणी, कधी, काय,
का बदललं: आणि कुठल्याही जुन्या क्षणी **परत जाता येतं.** लेखकाच्या
draft-वहीची उपमा: प्रत्येक खाडाखोड जपलेली, म्हणून "तीन दिवसांपूर्वीचं
वाक्य बरं होतं" वाटलं तर परत आणता येतं. Software मध्ये हे
अमूल्य: एक बदल app फोडतो, git ने **लगेच** आधीच्या चालत्या
क्षणी परत (Knight Capital ची $460M-रात्र, 1.13: त्यांच्याकडे
सुरक्षित परत-जाणं नव्हतं). "परत फिरता येणं" (Book 4, 4.5 चा
brake) git देतं: म्हणून engineers **न घाबरता** प्रयोग करतात.

**भाग 2: अनेक हात, एक code (branches + merge).** 30 लोक
एकाच code वर एकदम लिहिले तर गोंधळ (2.4 चा race, माणसांत!).
git ची युक्ती: प्रत्येकाने आपली वेगळी **शाखा** (branch) घ्यायची:
मुख्य code ला हात न लावता, स्वतःच्या प्रतीवर काम. काम झालं,
तपासलं, की ती शाखा मुख्यात **जोडायची** (merge). प्रत्येक झाडाची
वेगळी फांदी, नीट तपासून खोडाला जोडायची. आता 30 लोक
समांतर काम करतात, एकमेकांच्या पायात न येता.

**भाग 3 (सर्वात महत्त्वाचा): review-संस्कृती (code review).**
आणि इथे elite teams चं खरं रहस्य आहे. कुठलीही फांदी मुख्यात
जोडण्याआधी, **दुसरा engineer ती वाचतो आणि मंजूर करतो**
(pull request review). का? कारण: (1) दुसऱ्याची नजर तुमची
चूक पकडते (तुम्हाला न दिसलेली); (2) ज्ञान पसरतं (दोघांना
आता ते code कळतं, एकावर अवलंबित्व नाही); (3) दर्जा टिकतो
(review पास होणारंच आत). Google, आणि जगातल्या प्रत्येक
elite टीमचा लोखंडी नियम: **कुठलंही code एकट्याने मुख्यात
जात नाही; दुसऱ्याची मोहोर लागतेच.** (Book 4, 5.3 चा
"दुसऱ्याची झडती" इथे माणसांत; आणि AI-युगात reviewer कधी
agent ही असू शकतो, पण मोहोरीचं तत्त्व तेच.)

**सूत्र इथे:** review = दर्जा + ज्ञान-प्रसार विकत, थोडा वेग
विकून. एकट्याने थेट टाकणं जलद, पण चुका आणि एकाकी-ज्ञान.
Review थोडं मंद, पण चुका आधीच पकडल्या, ज्ञान वाटलं.
आणि हा सौदा elite teams नेहमी दर्जाच्या बाजूने करतात:
कारण "थोडा उशीर" स्वस्त, "production मधली चूक" महाग.

## महाग चूक

"घाई आहे, review वगळून थेट टाकतो, नंतर बघू." Elite teams
मध्ये review वगळणं ही जवळपास गुन्हा-मानली-जाणारी गोष्ट,
आणि कारण साधं: **review न झालेलं code हे न-तपासलेलं
गृहीत** आहे, आणि ते बहुधा गर्दीच्या-महत्त्वाच्या क्षणी फुटतं.
"घाई" हे review वगळायचं कारण नाही; उलट घाईच्या वेळी
review **जास्त** महत्त्वाचं (घाईत चुका जास्त). एकट्याने-थेट-
टाकणं आज 10 मिनिटं वाचवतं, उद्या production-bug चे 10
तास खातं. नियम: **मोहोर नेहमी, अपवाद नाही.**

## नकाशावर

```
Part 3 चा नकाशा (वाढत जाईल):
3.1  git: इतिहास-यंत्र (परत फिरता येणं) + branches (समांतर
     काम) + review (दुसऱ्याची मोहोर: दर्जा+ज्ञान-प्रसार)
```

**सूत्रावर:** elite शिस्तीची पहिली वीट: review चा सौदा (थोडा
वेग देऊन दर्जा घेणं). माणसांची चूकही "अपयश गृहीत धरा"
(Book 4) चा भाग: दुसऱ्याची नजर हा माणसातला brake.

## स्वतः बघा (5 मिनिटं)

तुम्ही लिहिलेलं काहीही (message, अर्ज) पाठवण्याआधी दुसऱ्याला
"वाचून बघ" म्हटल्यावर त्यांनी चूक/सुधारणा दाखवल्याचं आठवा:
तुम्हाला न दिसलेली. तीच code review ची ताकद: **तुमचे डोळे
तुमच्या चुकीला सरावलेले असतात; दुसऱ्याचे नाहीत.** म्हणून elite
teams एकमेकांचं सगळं वाचतात, न चुकता.

## विचार करा

आरतीच्या टीमने review सुरू केलं, चुका घटल्या. पण तरी काही
चुका review मधून निसटतातच (माणूस थकतो, घाईत बघतो).
आणि त्या production मध्ये पोहोचल्यावर गिऱ्हाईकाला दिसतात.
आरती विचारते: "माणसाची नजर चुकतेच. पण एकच चूक पुन्हा-
पुन्हा होऊ नये, आणि जुनं जमणारं नव्या बदलाने मोडू नये:
याची **आपोआप** खात्री कशी करायची? दर वेळी 30 लोकांनी
सगळं हाताने तपासणं अशक्य आहे."

> हवी ती आपोआप-तपासणी: आणि तिचं नाव testing. माणसाची
> नजर एकदाची; testing ची नजर दर वेळी, न थकता, न विसरता.
