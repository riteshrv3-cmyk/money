# Chapter 3.3 [SPINE]: CI/CD आणि सुरक्षित Deploy

आरतीच्या "आपोआप, सुरक्षित वाहतूक" या मागणीचं नाव CI/CD.
आणि त्यासोबत deploy सुरक्षित करण्याच्या युक्त्या: ज्यांच्या
गैरहजेरीने Knight Capital आणि CrowdStrike कोसळले (1.13).

**CI/CD म्हणजे काय (साध्या भाषेत).** दोन जोडलेल्या साखळ्या:
**CI (Continuous Integration):** कुणीही code बदललं की **आपोआप**:
build (जोडणी) + सगळे tests चालवा (3.2) + review-दार (3.1).
पास तरच पुढे. **CD (Continuous Deployment/Delivery):** पास
झालेलं code **आपोआप, सुरक्षितपणे** गिऱ्हाईकांपर्यंत. कारखान्याच्या
assembly-line ची उपमा: कच्चा माल (code-बदल) एका टोकाला;
प्रत्येक टप्प्यावर आपोआप तपासणी-दार; बाहेर पडतं ते तयार,
तपासलेलं उत्पादन. हाताने-रात्री-जागून चं काम यंत्राने, दर वेळी
सारखं, चुकल्याशिवाय.

**पण deploy हा सर्वात धोक्याचा क्षण: तीन सुरक्षा-युक्त्या.**
नवं code गिऱ्हाईकांपर्यंत नेणं म्हणजे चालत्या विमानाचं engine
बदलणं: इथेच सर्वात मोठे अपघात (Knight, CrowdStrike). म्हणून
elite teams तीन युक्त्या वापरतात:

```
1. Canary (कोळशाच्या खाणीतला पक्षी): नवं code आधी फक्त
   1-2% गिऱ्हाईकांना द्या. काही बिघडलं का बघा. ठीक असेल
   तरच हळूहळू सगळ्यांना. CrowdStrike ने हे केलं नाही: 85
   लाख यंत्रांना एकदम सदोष update = इतिहासातला सर्वात
   मोठा IT-बिघाड. एक canary त्यांना वाचवता आला असता.
2. Blue-green (दोन रंग): जुनं (blue) चालू ठेवून नवं (green)
   बाजूला तयार करा; तयार झाल्यावर वाहतूक हळूच green कडे
   वळवा. बिघडलं तर लगेच blue कडे परत (एका सेकंदात).
3. Feature flag (स्विच): नवं feature code मध्ये आहे पण
   "बंद" स्विचवर; हवं तेव्हा थोड्यांसाठी "चालू", बिघडलं तर
   कोड न बदलता लगेच "बंद". प्रयोग आणि सुरक्षा एकत्र.
```

तिन्हींचं एक तत्त्व (Book 4, 4.5 + 7.4 चे भाऊ, आणि 1.13
च्या प्रलयांचा थेट धडा): **कुठलाही बदल सगळ्यांना एकदम देऊ
नका; आधी थोड्यांवर, परत-फिरण्याचा रस्ता उघडा ठेवून.** हेच
elite deploy चं हृदय.

**आणि इथे एक थक्क करणारा विरोधाभास (elite teams चं खरं
रहस्य):** जे teams **जास्त वेळा** deploy करतात (दिवसातून
अनेकदा!) ते **कमी** अपघात करतात. कसं? कारण छोटे-वारंवार
बदल सुरक्षित असतात (एक छोटा बदल बिघडला तर शोधणं-दुरुस्त
करणं सोपं); मोठे-क्वचित बदल धोकादायक (शेकडो बदल एकदम,
काहीतरी फुटलं तर कशाने ते शोधणं अशक्य). Knight Capital
चा मोठा-क्वचित deploy विरुद्ध elite चा छोटा-वारंवार. धडा:
**वेग आणि सुरक्षा विरोधी नाहीत; छोटे-वारंवार-आपोआप बदल
दोन्ही देतात.**

## महाग चूक

"Deploy म्हणजे मोठा प्रसंग: महिन्यातून एकदा, रात्री, सगळं
एकदम, सगळे जागून." हीच जुनी, धोकादायक पद्धत: मोठे-क्वचित-
हाताने deploys = जास्त चुका, अवघड निदान (Knight ची रात्र).
Elite उलट: **छोटे, वारंवार, आपोआप, canary सह.** "deploy
भीतीदायक आहे" ही भावना म्हणजे तुमची deploy-पद्धत चुकीची
आहे याचं लक्षण: सुरक्षित पद्धतीत deploy इतका सामान्य होतो
की भीती उरत नाही. भीती हे सुधारणेचं आमंत्रण आहे, सहन
करण्याची गोष्ट नाही.

## नकाशावर

```
3.1-3.2  git | testing
3.3  CI/CD: आपोआप build+test+deploy साखळी; canary (थोड्यांना
     आधी) + blue-green + feature flag; छोटे-वारंवार = सुरक्षित;
     वेग आणि सुरक्षा एकत्र
```

**सूत्रावर:** इथे सूत्राला सुखद उलथापालथ: छोटे-वारंवार deploys
मध्ये वेग **आणि** सुरक्षा दोन्ही मिळतात: कारण जोखीम छोटी
राहते. काही ठिकाणी शहाणी रचना सौद्याचं गणितच बदलते.

## स्वतः बघा (5 मिनिटं)

तुमच्या फोनवरची apps आपोआप, वारंवार update होतात ना
(तुम्हाला कळतही नाही)? ते CI/CD. आणि कधीकधी एखादं नवं
feature "काही जणांना दिसतं, काहींना नाही" (feature flag/canary):
company आधी थोड्यांवर तपासतेय. तुम्ही रोज elite deploy-
शिस्तीच्या दुसऱ्या बाजूला उभे असता, नकळत.

## विचार करा

आरतीकडे आता पूर्ण शिस्त आहे. पण एका रात्री, सगळं असूनही,
app कोसळलंच: canary मधून निसटलेला एक bug. गिऱ्हाईकं
संतापली. दुसऱ्या दिवशी टीम-मीटिंगमध्ये आरतीला मोह झाला:
"कोणी केलं हे? कोणाची चूक?" पण तिला जाणवलं की दोषी
शोधल्याने पुढच्या वेळी लोक चुका **लपवतील**, सांगणार नाहीत.
"चूक झाली की काय करायचं: दोषी शोधायचा, की काहीतरी वेगळं?"

> हाच elite teams आणि सामान्य teams मधला सर्वात मोठा
> फरक: चूक झाल्यावरची **संस्कृती.** दोषी शोधणं की रचना
> शिकणं. या एका निवडीवर टीम टिकते किंवा कुजते. पुढचा
