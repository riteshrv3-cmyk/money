# Chapter 3.2 [SPINE]: Testing चे थर

आरतीच्या "आपोआप, न थकता तपासणी" या मागणीचं नाव testing.
Book 4 त हे agent साठी evals म्हणून भेटलं (5.1); इथे ते
software साठी, आणि त्याला वेगळे **थर** आहेत: प्रत्येक थर
वेगळी चूक पकडतो.

**Testing म्हणजे काय.** code ची **आपोआप परीक्षा**: "हे code
या-इनपुटला हे-उत्तर देतं का?" एकदा लिहिली की **दर वेळी**
चालते: माणूस थकतो, विसरतो; test न थकता, न विसरता, प्रत्येक
बदलावर तपासते. गुणवत्ता-नियंत्रकाची उपमा: कारखान्यात प्रत्येक
माल तपासणारा, न कंटाळता, तोच निकष लावणारा. Testing हा
elite teams चा तो नियंत्रक.

**तीन थर (प्रत्येक वेगळी चूक पकडतो):**

```
1. Unit test (सुटा भाग):    एक छोटा तुकडा एकटा तपासणं.
   "भाव-मोजणीचं function 2 किलो x 40 = 80 देतं का?"
   जलद, भरपूर, स्वस्त. पाया.
2. Integration test (जोड):  दोन-तीन भाग मिळून तपासणं.
   "ऑर्डर-सेवा + database + payment मिळून नीट चालतात का?"
   कमी, थोडे मंद, पण खरे-जगाजवळ.
3. End-to-end test (पूर्ण):  गिऱ्हाईकासारखं पूर्ण प्रवास.
   "app उघडून, साखर शोधून, ऑर्डर करून, पैसे भरून: सगळं
   जमतं का?" सर्वात कमी, सर्वात मंद, सर्वात खरे.
```

**थरांचं तत्त्व (testing pyramid): खाली भरपूर, वर थोडे.**
भरपूर unit tests (जलद-स्वस्त, रोज हजारो वेळा चालतात),
मध्यम integration, थोडे end-to-end (मंद-महाग). का? कारण
unit tests सेकंदात चालतात, end-to-end मिनिटं खातात: सगळंच
end-to-end केलं तर testing इतकं मंद की कुणी चालवणारच
नाही. पाया रुंद, कळस अरुंद: हीच शहाणी रचना.

**सर्वात मोठा फायदा: घसरण-रोध (regression).** आजची चूक
दुरुस्त केली + तिची test लिहिली, तर उद्या कुणीतरी तेच पुन्हा
मोडलं की **test लगेच ओरडते**: production आधी. Book 4, 5.5
चा "जुनं जमणारं नव्याने बिघडू नये" इथे शब्दशः. Elite teams
चा नियम: **bug सापडला की आधी त्याची test लिहा (म्हणजे
तो पुन्हा कधीच परत येणार नाही), मग दुरुस्त करा.** प्रत्येक
चूक एकदाच; test कायमचा पहारा.

**सूत्र इथे:** testing = आत्मविश्वास + घसरण-रोध विकत, "आधीचा
वेळ" विकून. Test लिहायला वेळ लागतो (आजचा खर्च); पण मग
प्रत्येक बदल **न घाबरता** करता येतो (test राखतो: Book 4,
5.5 ची हिंमत). Test नसलेलं मोठं code म्हणजे प्रत्येक बदलाला
भीती; test असलेलं म्हणजे धीट प्रयोग. वेग testing मुळे मरत
नाही, वाढतो: फक्त सुरुवातीचा खर्च दिसतो, पुढची बचत नाही.

## महाग चूक

"Testing म्हणजे वेळ वाया; code तर चालतंय." सर्वात महाग
अल्पदृष्टी. Test नसलेलं code सुरुवातीला जलद वाटतं, पण
लवकरच प्रत्येक बदल भीतीदायक होतो ("हे बदललं तर काय
मोडेल?"), आणि टीम बदल करणंच टाळते (2.11 चा "चालतंय ते
मोडू नको" चा भाऊ): app गोठतं. उलट, test असलेलं code
वर्षानुवर्षं धीटपणे बदलता येतं. Test हा "वेळ वाया" नाही, तो
**भविष्यातल्या वेगाचा विमा** आहे. जगातलं प्रत्येक टिकाऊ मोठं
software भरपूर testing वर उभं आहे: अपवाद नाही.

## नकाशावर

```
3.1  git: इतिहास + branches + review
3.2  testing: तीन थर (unit जलद-भरपूर / integration / e2e मंद-
     थोडे); घसरण-रोध; bug -> आधी test मग दुरुस्ती; वेगाचा विमा
```

**सूत्रावर:** testing चा सौदा वेळेत उलटतो: आजचा खर्च, उद्याची
मुक्ती. Elite teams दीर्घ नजरेने हा सौदा करतात; नवखे आजच्या
वेगाच्या मोहात तो टाळतात आणि उद्या गोठतात.

## स्वतः बघा (5 मिनिटं)

तुम्ही एखादं महत्त्वाचं गणित/हिशेब करताना "एकदा तपासून बघू"
म्हणून उलटा हिशेब करता (80 / 40 = 2 किलो, बरोबर): ती एक
मानसिक unit test आहे. आता कल्पना करा हे तपासणं **आपोआप,
दर वेळी** झालं तर किती निश्चिंत. Software चं testing तेच, फक्त
यंत्राने, हजारो वेळा, न थकता.

## विचार करा

आरतीच्या टीमकडे आता git, review, testing आहे. पण तरी एक
अडचण: एका engineer ने बदल केला, review झालं, tests पास
झाले: पण ते **गिऱ्हाईकांपर्यंत पोहोचवायला** (deploy) दर वेळी
कुणीतरी हाताने, रात्री जागून, अनेक पायऱ्या करायचं: आणि तिथेच
चुका (एक server विसरणं: Knight Capital!). "बदल तयार आहे,
पण तो सुरक्षित, आपोआप, चुकल्याशिवाय गिऱ्हाईकांपर्यंत कसा
न्यायचा?"

> हवी ती आपोआप, सुरक्षित वाहतूक: build -> test -> deploy
> ची यंत्र-साखळी. तिचं नाव CI/CD, आणि ती elite teams च्या
> वेगाचं रहस्य आहे. पुढचा chapter.
